ВЫЧИСЛЕНИЕ HMAC.

1. Сгенерируем 256-битовый ключ.
~$ openssl rand -hex 32
cb3a421be5782f518f225ea93f1d193958cbaaabad6d7eaa80e4d5815b296374

2. Посчитаем HMAC для foo.h через openssl dgst:
~$ openssl dgst -sha3-256 -mac HMAC -macopt hexkey:cb3a421be5782f518f225ea93f1d193958cbaaabad6d7eaa80e4d5815b296374 foo.h
HMAC-SHA3-256(foo.h)= b10f22953327160c2137466f3047da131ee8b940c6bb827209825900a2daea34

2. Посчитаем HMAC для foo.h через openssl mac:
~$ openssl mac -digest SHA3-256 -macopt hexkey:cb3a421be5782f518f225ea93f1d193958cbaaabad6d7eaa80e4d5815b296374 -in foo.h HMAC
B10F22953327160C2137466F3047DA131EE8B940C6BB827209825900A2DAEA34


Внутри openssl dgst -sha3-256 -mac HMAC -macopt hexkey:... foo.h работает
стандартный HMAC, только в качестве хэша взят SHA3-256.

Обозначим:
    H = SHA3-256;
    K = ключ из hexkey: — это не строка "cb3a...", а байты cb 3a 42 ... 74, всего 32 байта;
    m = всё содержимое файла foo.h в байтах;
    B = размер блока для HMAC-SHA3-256. Для SHA3-256 это rate = 1088 бит = 136 байт.

Формула HMAC:
HMAC(K, m) = H( (K' xor opad) || H( (K' xor ipad) || m ) )

где || — конкатенация, xor — побайтовый XOR.

Что происходит по шагам:

    Ключ K нормализуется до размера блока B = 136 байт.
    Твой ключ длиной 32 байта, значит он дополняется нулями до 136 байт:
    text

    K' = K || 00 00 ... 00   // 104 нулевых байта

    Если бы ключ был длиннее 136 байт, его сначала хэшировали бы через
    SHA3-256, а потом дополняли нулями. Здесь этого нет.

    Считаются два фиксированных блока:

    ipad = 0x36, повторённый 136 раз
    opad = 0x5c, повторённый 136 раз

    Внутренний хэш:

    inner = H( (K' xor ipad) || m )

    То есть сначала идёт 136-байтовый блок K' xor ipad, а сразу за ним — всё содержимое foo.h.
    Имя файла foo.h в хэш не попадает, оно только для вывода openssl.

    Внешний хэш:
    text

    result = H( (K' xor opad) || inner )

    То есть сначала идёт 136-байтовый блок K' xor opad, а за ним — 32-байтовый
    внутренний хэш inner, потому что SHA3-256 выдаёт 32 байта.

    Итог переводится в hex и печатается после =.
    Строка HMAC-SHA3-256(foo.h)= — это только человекочитаемая метка.




ФОРМИРОВАНИЕ КЛЮЧА ИЗ ПАРОЛЯ В КОМАНДНОЙ СТРОКЕ (KDF - Key Derivation Function).

    Для порождения ключа шифрования из пароля применяется новая подко манда
openssl kdf, добавленная в версии OpenSSL 3.0. Она документирована на странице
руководства openssl-kdf:

~$ man openssl-kdf

Прежде чем формировать ключ, сгенерируем 128битовую соль:

~$ openssl rand -hex 16

Теперь можно сформировать 256битовый ключ симметричного шифро вания.
Воспользуемся KDF scrypt с рекомендуемыми OWASP параметрами, стойкими к полному
перебору, и паролем SuperPa$$w0rd:

~$ openssl kdf \
	-keylen 32 \
	-kdfopt ‘pass:SuperPa$$w0rd’ \
	-kdfopt hexsalt:cf0e0acf943629ecffea41c87bab94d4 \
	-kdfopt n:65536 -kdfopt r:8 -kdfopt p:1 \
	SCRYPT

ШИФРОВАНИЕ И РАСШИФРОВАНИЕ С ПОМОЩЬЮ RSA В КОМАНДНОЙ СТРОКЕ.

man openssl-pkeyutl

RSA обычно применяется для шифрования сеансового ключа, который затем
используется для шифрования полезных данных.

Сгенерируем 256битовый сеансовый ключ:
~$ openssl rand -out session_key.bin 32

Воспользуемся подкомандой openssl pkeyutl с нашим открытым ключом RSA для
шифрования сеансового ключа:

~$ openssl pkeyutl \
	-encrypt \
	-in session_key.bin \
	-out session_key.bin.encrypted \
	-pubin \
	-inkey rsa_public_key.pem \
	-pkeyopt rsa_padding_mode:oaep \
	-pkeyopt rsa_oaep_md:sha256 \
	-pkeyopt rsa_mgf1_md:sha256

Обратите внимание на параметр -pkeyopt rsa_padding_mode:oaep. Он оз начает, что
при RSAшифровании нужно использовать оптимальное до- полнение асимметричного
шифрования (Optimal Asymmetric Encryption Padding – OAEP), определенное в
стандарте PKCS #1 v2.0. Настоятельно ре комендуется использовать именно этот
тип дополнения, потому что он счи тается самым стойким. Дополнение типа PKCS #1
v1.5 может сделать ваш шифртекст уязвимым для атаки с оракулом дополнения
Блейхенбахера.

Посмотрим на созданные нами файлы:
~$ cksum session_key.bin*
477920880 32 session_key.bin
550986498 512 session_key.bin.encrypted

Отметим, что длина входного сеансового ключа равна всего 32 байта (256 бит), но
в зашифрованном виде он занимает уже 512 байт (4096 бит), поскольку размер
блока выходного шифртекста RSA равен длине ключа.

Попробуйте зашифровать сеансовый ключ несколько раз и убедитесь, что размер
зашифрованного файла всегда один и тот же, но контрольная сумма всякий раз
разная. Хотя само RSA шифрование детерминировано, допол нение OAEP таковым не
является, в результате чего шифртекст получается недетерминированным.


OAEP vs. PKCS#1 v1.5

Характеристика	RSA_PKCS1_PADDING (v1.5)	RSA_PKCS1_OAEP_PADDING (OAEP)
---------------+-------------------------------+------------------------------------
Безопасность	Считается устаревшим,		Доказанно безопасен, рекомендуется
		подвержен атакам.		для новых приложений.
---------------+-------------------------------+------------------------------------
Макс. размер	RSA_size - 11 байт		RSA_size - 42 байт для SHA-1
сообщения					RSA_size - 66 байт для SHA-256
---------------+-------------------------------+------------------------------------
Случайность	Есть, но менее надёжная		Криптографически стойкая случайность

Максимальный размер сообщения для RSA-OAEP считается так:
	max_message_len = k - 2 * hLen - 2,
где
  k     — размер модуля RSA в байтах (RSA_size, например, 256 для 2048 бит);
  hLen  — длина хеша, используемого в OAEP (в байтах);
  2     — это один байт 0x00 в начале и один байт 0x01 — разделитель перед
          сообщением.

RSA4096_size = RSA4096_bits (4096 бит) / 8 бит = 512 байт
sha256_hlen = 256 бит / 8 бит = 32 байта
max_message_len = 512 - 2 * 32 - 2 = 512 - 66 = 446 байт

Мы успешно зашифровали небольшой файл. А что, если попытаться за шифровать файл
побольше? Попробуем. Сначала сгенерируем файл нужного размера:

$ seq 20000 >somefile.txt

Получился файл примерно на 100 КБ. Зашифруем его:

~$ openssl pkeyutl \
	-encrypt \
	-in somefile.txt \
	-out somefile.txt.encrypted \
	-pubin \
	-inkey rsa_public_key.pem \
	-pkeyopt rsa_padding_mode:oaep
Public Key operation error
C011FAE8677F0000:error:0200006E:
rsa routines:ossl_rsa_padding_add_PKCS1_OAEP_mgf1_ex:
data too large for key size:crypto/rsa/rsa_oaep.c:87:

Мы получили ошибку, означающую, что входные данные слишком велики для ключа
такого размера. Дело в том, что RSA не умеет шифровать данные длиннее ключа за
одну операцию. А если используется дополнение, то максимально допустимая длина
открытого текста еще меньше. При использовании дополнения типа OAEP
максимальная длина входных данных равна длине ключа минус 42 (в нашем случае
4096 – 42 = 4054 байта). Если нужно зашифровать данные большей длины, то
придется использовать симметричный сеансовый ключ.

Настало время расшифровать то, что мы зашифровали, и сравнить с ори гиналом.
Для расшифрования нужно передать openssl pkeyutl пару ключей, а не просто
открытый ключ:

~$ openssl pkeyutl \
	-decrypt \
	-in session_key.bin.encrypted \
	-out session_key.bin.decrypted \
	-inkey rsa_keypair.pem \
	-pkeyopt rsa_padding_mode:oaep \
	-pkeyopt rsa_oaep_md:sha256 \
	-pkeyopt rsa_mgf1_md:sha256

Проверим контрольную сумму:

~$ cksum session_key.bin*
477920880 32 session_key.bin
477920880 32 session_key.bin.decrypted
550986498 512 session_key.bin.encrypted

Как видим, размеры и контрольные суммы файлов session_key.bin и
session_key.bin.decrypted одинаковы, т. е. расшифрованный файл совпадает с

[!] MGF1 (Mask Generation Function 1)

Это функция из стандарта PKCS#1 (RFC 8017), которая превращает короткий
seed в псевдослучайную последовательность произвольной длины.

Как работает:
- Берётся хеш-функция H (например, SHA-256) с длиной выхода hLen.
- Вычисляется T = H(seed || 0) || H(seed || 1) || H(seed || 2) || ...,
  где счётчик — 4 байта big-endian.
- Результат обрезается до нужной длины L.

Где используется в OAEP:
- Для маскирования блока данных: dbMask = MGF1(seed, k - hLen - 1).
- Для маскирования seed: seedMask = MGF1(maskedDB, hLen).

Параметр в OpenSSL:
- Задаётся через -pkeyopt rsa_mgf1_md:sha256 или в C через
  EVP_PKEY_CTX_set_rsa_mgf1_md().
- Обычно совпадает с хешем OAEP (rsa_oaep_md), но может быть и другим.

Важно:
- MGF1 — не шифрование и не KDF для паролей, а просто генератор маски.
- Стойкость зависит от выбранной хеш-функции. SHA-1 устарел,
  рекомендуется SHA-256 и выше.
